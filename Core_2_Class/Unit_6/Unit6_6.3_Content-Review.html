How to Use This Page

Everything here is a symptom-to-cause map. The exam will not ask you to define a blue screen; it will describe one and ask what you would do. Read each symptom and try to name the likely cause before you read the answer — that is the skill being tested, and this page is built to let you practice it.

Part 1 — Malware Removal, in Order (Objective 2.6)

This objective is about a sequence. The exam asks what comes next, so the order is the content.

StepWhat You DoWhy Here
1. Investigate and verify malware symptomsConfirm malware is actually the causePlenty of "virus" tickets are a failing drive or a bad update
2. Quarantine infected systemsDisconnect from the networkStops it spreading while you work
3. Disable System Restore in WindowsTurn off restore pointsMalware hides in restore points and reinfects from them
4. Remediate infected systemsClean or repair the systemThe removal itself
5. Update anti-malware softwareGet current definitionsSignature scanning only catches what it knows
6. Use scanning and removal techniquesScan in safe mode or the preinstallation environmentMalware that blocks removal usually cannot run there
7. Reimage if requiredReinstall from known-good mediaThe only certain answer when removal cannot be trusted
8. Schedule scans and run updatesSet recurring protectionPrevents the next one
9. Enable System Restore and create a restore pointTurn it back on, from a clean stateThe new baseline is a clean machine
10. Educate the end userExplain what happened and how to avoid itLast for a reason — it is the step that prevents the repeat visit
The Book Groups These Into Seven

Your textbook presents the same procedure as seven steps with sub-steps, combining updating anti-malware and the scanning techniques under remediation. Same order, split differently. Learn CompTIA's ten, because that is what the exam numbers — the book's grouping is shown here only so the two do not confuse you.

Two Steps People Get Wrong

Disable System Restore before remediating, not after. If you clean the machine and leave infected restore points in place, a single restore reinfects it.

Educate the user last, and actually do it. It feels optional because the machine already works. It is the only step that changes whether you see this machine again next month.

A Real Example You Will Meet on the Job

A user's machine is infected and they have a folder of documents that exist nowhere else. The honest sequence is: get the system running just well enough to recover those files, copy them off and scan them separately, and then wipe the machine and restore from a known-good image. Removal tools are good; they are not a guarantee. When the data matters, the safest machine is the one you rebuilt.

Part 2 — Troubleshooting Windows (Objective 3.1)

SymptomWhere to Look First
Blue screen of death (BSOD)Recent driver or hardware change; the stop code; Event Viewer's System log. Roll back the driver you installed last.
Sluggish performanceTask Manager, sorted by CPU and then memory; disk space; startup programs
Boot problemsBoot order, boot device, and the Windows Recovery Environment. Was something installed or changed?
Frequent shutdownsOverheating, power supply, or a driver fault — Event Viewer narrows which
Services not startingThe Services snap-in and its dependencies; Event Viewer for the failure reason
Applications crashingEvent Viewer's Application log; updates; repair or reinstall the application
Low memory warningsTask Manager's memory use; the page file; too many applications open
USB controller resource warningsDevice Manager; too many devices on one controller; a powered hub
System instabilityDrivers, overheating, failing storage, and recent changes — in that order
No OS foundBoot order, a disconnected drive, a failed drive, or damaged boot files
Slow profile loadRoaming profile size, network and domain controller reachability, log-in scripts
Time driftTime service and its source; the CMOS battery; domain time sync. More than a nuisance — authentication fails when clocks disagree.

Common Troubleshooting Steps

  • Reboot — genuinely fixes a category of problems, and is the correct first step more often than technicians like to admit
  • Restart services — the targeted version of a reboot
  • Uninstall, reinstall, or update applications
  • Add resources — when the machine is genuinely short of memory or storage
  • Verify requirements — the Unit 1 question: can this machine run this software at all?
  • System file check — sfc /scannow, from Unit 2
  • Repair Windows, restore, reimage, or roll back updates — in increasing order of disruption

Least Disruptive First

The order above is the answer to a whole family of exam questions. When several options would fix the problem, the right answer is almost always the least disruptive one that could work — restart the service before rebooting the server, repair before reimaging, roll back one update before restoring the whole system.

Reimaging fixes everything and costs the user their afternoon. It is the last resort, not the fast one.

Part 3 — Mobile Troubleshooting (Objectives 3.2 and 3.3)

Common Mobile Issues (3.2)

SymptomLikely Causes
Application fails to launch, close, or updateStorage full, OS version too old, corrupted app data
Slow performanceStorage nearly full, background apps, an aging battery
Battery life issues and swollen batteryNormal wear versus a safety hazard — a swollen battery is removed from service immediately and disposed of properly
Random rebootsFailing hardware, an OS fault, or a badly behaved application
Connectivity issues — Bluetooth, Wi-Fi, NFC, AirDropRadio disabled, out of range, pairing lost, or a profile restriction
Screen does not autorotateRotation lock, or a failed sensor

Mobile Security Issues (3.3)

These are the symptoms that mean something is wrong rather than merely broken:

  • Unexpected application behavior — an app doing something it has no reason to do
  • Leaked personal files or data
  • Data-usage limit notification — something is transmitting that should not be
  • High network traffic — the same signal, seen from the network
  • Sluggish response time — when combined with the above, not just an old phone
  • Fake security warnings — a browser page pretending to be the system
A Real Example You Will Meet on the Job

A user says their phone is "slow and hot" and that they are suddenly hitting their data limit every month. Separately, each is unremarkable — phones age, plans change. Together they describe something running constantly and transmitting. Check installed applications and their permissions, review data usage per application, and treat it as a security issue rather than a performance one. Symptoms that are boring alone are meaningful in combination.

Part 4 — Troubleshooting Security Issues (Objective 3.4)

SymptomWhat It Usually Means
Unable to access the networkMalware blocking connectivity, or a security control doing its job
Desktop alerts and false alerts regarding antivirus protectionA fake warning designed to make the user install or pay for something
Altered system or personal files, including missing or renamed filesA hallmark of ransomware — check before anything else
Unwanted notifications within the OSBrowser notification permissions granted to a hostile site, or adware
OS update failuresMalware preventing updates so it cannot be removed
Random or frequent pop-upsAdware, or a browser extension
Certificate warningsAn expired certificate, a wrong system clock, or traffic being intercepted
RedirectionA hijacked browser, a changed hosts file, or altered DNS settings

Three Symptoms, One Cause

Update failures, no network access, and antivirus that will not update are the same finding: something on the machine is preventing its own removal. Any one of them on its own is a configuration problem. Together they are an infection, and the answer is the step-6 approach — scan from safe mode or a preinstallation environment where the malware cannot run.

Part 5 — Remote Access Technologies (Objective 4.9)

TechnologyWhat It IsWhen It Fits
RDPRemote Desktop Protocol — full graphical control of a Windows machineAdministering a Windows system as though you were sitting at it
VPNAn encrypted tunnel into a private networkReaching internal resources from outside; often the prerequisite for everything else here
VNCCross-platform screen sharing and controlMixed environments where RDP is unavailable
SSHEncrypted command-line accessLinux and network devices; low bandwidth and highly scriptable
RMMRemote monitoring and management — agent-based tools that watch and administer many machinesManaged service providers and internal IT at scale
MSP toolsThe platforms built around RMM for ticketing, patching, and reportingOutsourced IT support
File transfer softwareMoving files to and from a remote systemDelivering a fix or collecting logs
Desktop management softwareCentral configuration and software deploymentStandardizing a fleet of workstations
Video-conferencing softwareScreen sharing with a user, with their consent and participationWalking a user through something they must do themselves

Security Considerations

Every remote access method is a door into a system, which is why the objective pairs them with security considerations. The recurring ones: use encrypted protocols rather than unencrypted equivalents; never expose RDP directly to the internet — put it behind a VPN; require multifactor authentication for remote access; apply least privilege to remote accounts as you would to local ones; and log and monitor remote sessions, since a remote connection nobody can account for is an incident.

The Attack This Objective Exists to Prevent

Exposed RDP with a weak password is one of the most common ways ransomware enters a small organization. The attacker does not need an exploit — they run a dictionary attack against an open port and sign in. Every control in Unit 5 applies here: account lockout, multifactor authentication, least privilege, and a VPN in front of the whole thing.

Part 6 — The Basics of Artificial Intelligence (Objective 4.10)

This objective is new to the A+ and is about using AI responsibly in IT work, not about building it.

What It Is

AI tools generate answers from patterns in training data. They do not look anything up unless they are given a tool to do so, and they do not know whether an answer is correct — they produce what is probable. That single fact explains nearly every risk below.

Risks and Considerations

  • Inaccurate or fabricated output — an AI will produce a confident, well-formatted answer that is wrong, including invented commands, settings, and citations
  • Data privacy — what you paste into a public AI tool may leave your organization. Customer data, credentials, and internal documents do not belong in one.
  • Intellectual property and licensing — generated content may carry obligations or restrictions
  • Bias — output reflects the data it was trained on
  • Acceptable use — organizations increasingly have policies governing which AI tools may be used for what, and a technician is expected to follow them

The Technician's Rule for AI

Use it to draft, never to decide. An AI is good at producing a first version of a ticket summary, a script, or an explanation for a user. It is not a source of fact, and it is not accountable for the outcome — you are.

Verify anything it tells you against documentation before you act on it, exactly as you would verify advice from a forum post. In this unit's "Check the AI" lab, you will do precisely that with an AI answer to an A+ question, and finding the error yourself is more convincing than being warned about it.

One more rule, directly from the testing policies: no AI assistance during a certification exam, ever. Using one is cheating, and for an online proctored exam it is grounds for immediate termination.

How to Think Like a Troubleshooter

Every symptom table on this page is a shortcut. The underlying method is the same one that works when the symptom is not in any table:

  1. Establish what changed. Almost every fault follows a change — an update, an install, a setting, a new device. "It worked yesterday" is the most useful sentence a user can give you.
  2. Reproduce it. A problem you can trigger on demand is a problem you can test a fix against.
  3. Narrow by halves. Is it this machine or the network? This user or every user? This application or everything? Each answer eliminates half the possibilities.
  4. Change one thing at a time, and test after each. Two changes at once means you will never know which worked.
  5. Choose the least disruptive fix that addresses the cause rather than the symptom.
  6. Document what you did — which brings you back to objective 4.1, and the first thing you learned in Unit 1.
Six Units, One Loop

You opened this course writing a help-desk ticket, and you are closing it by writing a better one. That is not a coincidence in the design — it is what the job looks like. Everything in between was the knowledge that lets the ticket say something useful.

Unit 6 Content Recap

  • Malware removal is a ten-step sequence; disable System Restore before remediating, and educate the user last
  • When removal cannot be trusted and the data matters: recover the files, then reimage
  • Windows symptoms map to causes — and the right fix is the least disruptive one that could work
  • Time drift breaks authentication, not just clocks
  • Mobile symptoms that are unremarkable alone can be meaningful in combination
  • Update failures, blocked network access, and antivirus that will not update are one finding: the malware is defending itself
  • Remote access methods are doors — encrypted protocols, multifactor authentication, least privilege, and logging apply to all of them
  • Never expose RDP directly to the internet
  • AI is for drafting, not deciding; verify before you act, and never use it during a certification exam
  • When no table has your symptom: what changed, reproduce, narrow by halves, one change at a time, least disruptive fix, document
